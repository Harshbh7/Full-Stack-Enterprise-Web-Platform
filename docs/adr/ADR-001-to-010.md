# EduSphere — Architecture Decision Records (ADR-001 to ADR-010)

This document formalizes the foundational architectural and design decisions adopted in EduSphere.

---

## ADR-001: Selection of React 18 with TypeScript for Frontend SPA

- **Status:** ACCEPTED
- **Context:** The frontend requires complex state orchestration (multi-tenant routing, role-based views, real-time classroom updates, course progress, quiz runners) while maintaining high responsiveness across device viewports.
- **Decision:** Use React 18 with TypeScript, Vite as build tool, and Material UI (MUI v6) as the design framework.
- **Alternatives Considered:**
  1. *Next.js (App Router):* Offers SSR, but introduces complexity with stateful WebSockets, client-side session tokens, and higher deployment overhead in containerized single-tier Nginx targets.
  2. *Vue 3 / Svelte:* Strong options, but the capstone course mapping (CAP646 / CAP774) emphasizes enterprise React ecosystem practices.
- **Consequences:** Provides type safety across DTO interfaces, rapid hot module replacement via Vite, and comprehensive component ecosystem with MUI.

---

## ADR-002: Selection of Node.js with Express and TypeScript for Backend

- **Status:** ACCEPTED
- **Context:** The backend must handle high I/O concurrency (real-time chat, WebSocket polling, REST APIs, cache invalidation) with minimal latency while sharing data contracts with the frontend.
- **Decision:** Build the backend using Node.js, Express.js, and TypeScript.
- **Alternatives Considered:**
  1. *NestJS:* Implements enterprise IoC, but introduces heavy decorator abstraction that can obscure raw architectural layers during academic faculty evaluation.
  2. *Django / Spring Boot:* Excellent enterprise backends, but violates the unified TypeScript full-stack constraint.
- **Consequences:** Clean 6-layer architecture without unnecessary runtime overhead; allows direct inspection of middleware pipelines.

## ADR-003: Selection of MongoDB with Mongoose ODM for Persistence

- **Status:** ACCEPTED
- **Context:** LMS curricula have hierarchical, polymorphic entities (courses have modules; modules have varied lesson types such as video, markdown, quiz, assignments). Schemas evolve dynamically per course format.
- **Decision:** Utilize MongoDB 8.x with Mongoose ODM.
- **Alternatives Considered:**
  1. *PostgreSQL with Prisma:* Excellent relational guarantees, but requires extensive schema migration churn when lesson content types and quiz option structures evolve.
- **Consequences:** Embedded document performance for modules/lessons; fast reads. Requires strict application-level tenant isolation and compound indexing.

## ADR-004: Multi-Tenancy Strategy (Logical Discriminator Isolation)

- **Status:** ACCEPTED
- **Context:** EduSphere must support hundreds of independent educational organizations on shared hardware without data leakage.
- **Decision:** Adopt a **Shared Database, Shared Process, Discriminator-Partitioned** model. All tenant entities contain a indexed `tenantId` field. The `BaseRepository` automatically applies `tenantId` scoping to all queries.
- **Alternatives Considered:**
  1. *Database-per-Tenant:* Maximum isolation, but massive resource overhead (connection pool limits) and complex migration management across hundreds of databases.
  2. *Schema-per-Tenant:* Not natively supported in standard MongoDB clusters.
- **Consequences:** Maximum resource efficiency, simplified automated backups and migrations, with strict reliance on automated isolation tests.

## ADR-005: Authentication Strategy (Stateless JWT + Refresh Token Rotation)

- **Status:** ACCEPTED
- **Context:** Stateful sessions stored in memory limit horizontal scalability. Long-lived access tokens pose severe security vulnerabilities if intercepted.
- **Decision:** Use short-lived Access Tokens (15 minutes) containing user ID, role, and tenant ID. Pair with cryptographically random Refresh Tokens (7-day validity) stored in hashed format in Redis/Mongo with automatic rotation and family reuse detection.
- **Alternatives Considered:**
  1. *Server-Side Session Cookies in Redis:* Simpler token invalidation, but introduces Redis lookup latency on every single authenticated request.
  2. *Long-Lived JWT without Refresh:* Unacceptable security vulnerability in enterprise applications.
- **Consequences:** Zero database hit for authenticated API requests; secure single-use refresh rotation detects token theft instantly.

## ADR-006: Redis Caching Architecture (Cache-Aside + Mutation Invalidation)

- **Status:** ACCEPTED
- **Context:** Course catalogs, popular courses, tenant branding, and dashboard telemetry are read frequently but updated infrequently. Repeated database reads cause database contention.
- **Decision:** Integrate Redis 7+/Valkey 9+ using the Cache-Aside pattern. All cache keys follow tenant-partitioned naming (`tenant:{tenantId}:{entity}:{scope}`). Services invalidate matching keys on data mutations.
- **Alternatives Considered:**
  1. *In-Memory Node Cache (node-cache):* Memory leaks under high load; cannot share cache across clustered backend instances.
  2. *Write-Through Caching:* Adds latency to mutation paths without significant benefit for read-heavy LMS workloads.
- **Consequences:** p95 read latencies drop from ~120ms to <10ms; requires disciplined invalidation calls in service mutation methods.

## ADR-007: Real-Time Communication via Socket.IO

- **Status:** ACCEPTED
- **Context:** Announcements, classroom chat, and unread notifications must reach connected students immediately without manual page reloads or aggressive HTTP polling.
- **Decision:** Use Socket.IO with JWT authentication handshake and tenant-scoped room partitioning.
- **Alternatives Considered:**
  1. *Raw WebSockets (ws):* Lacks built-in room abstractions, automatic reconnection logic, and HTTP long-polling fallback.
  2. *Server-Sent Events (SSE):* Unidirectional only; cannot handle bi-directional classroom chat.
- **Consequences:** Out-of-the-box room isolation, automatic exponential backoff reconnection, and seamless integration with Redis adapter.

---

## ADR-008: 6-Tier Layered Architecture Pattern

- **Status:** ACCEPTED
- **Context:** Enterprise applications must maintain clean separation of concerns, avoiding monolithic route handlers with embedded business logic or database queries.
- **Decision:** Enforce a strict 6-tier pipeline: Route → Middleware → Controller → Service → Repository → Database.
- **Alternatives Considered:**
  1. *Controller-Direct-to-ORM (Fat Controller):* Rapid for trivial CRUD, but untestable and violates Single Responsibility Principle.
- **Consequences:** Every layer is independently unit-testable; repositories can be mocked in service tests; business rules remain database-agnostic.

---

## ADR-009: Testing Pyramid Strategy

- **Status:** ACCEPTED
- **Context:** The platform requires rigorous automated quality gates to satisfy academic defense and prevent regression.
- **Decision:** Implement a 4-level test pyramid:
  1. *Unit Tests (Vitest):* Services, utility functions, Zod schemas, Redux reducers.
  2. *Integration Tests (Supertest):* API endpoints, authentication flows, token rotation, tenant isolation.
  3. *Frontend Component Tests (React Testing Library):* Form validations, permission-based UI rendering.
  4. *End-to-End Tests (Playwright):* Full browser user journeys across roles.
- **Consequences:** High confidence before deployment; test execution integrated into GitHub Actions CI pipeline.

---

## ADR-010: Containerized Deployment via Docker & Docker Compose

- **Status:** ACCEPTED
- **Context:** Faculty, evaluators, and developers must be able to boot the entire platform (Frontend, Backend, Database, Cache) with a single command without installing manual dependencies.
- **Decision:** Supply production-grade multi-stage Dockerfiles and a root `docker-compose.yml` declaring all services with automated health checks and persistent volume mounts.
- **Alternatives Considered:**
  1. *Manual Local Setup Instructions:* Error-prone due to varying OS versions, Node versions, and service daemons.
  2. *Kubernetes (k8s):* Excessive operational complexity for university evaluation environment.
- **Consequences:** One-command startup (`docker compose up --build`), repeatable environment across all machines.
